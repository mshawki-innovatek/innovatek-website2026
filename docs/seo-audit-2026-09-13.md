# Innovatek SEO audit and implementation

Audit started 13 September 2026; local verification completed 14 September, Cairo time. Canonical site: **https://www.innovatek-swd.com**, confirmed by the owner. The similarly named `.ae` website is unrelated and was excluded from the implementation.

## What the missing search result tells us

Not appearing for “donation system” does not establish that Google has excluded the website. The live homepage and Arabic homepage returned 200, allowed indexing and exposed canonical links. The live robots file allowed crawling. Search Console access opened the property setup screen, not a verified dashboard for this site, so Google's actual indexing reasons, selected canonical, query impressions and positions could not be established.

The live sitemap still contained 16 URLs, including retired solutions pages, at audit time. It represents an older deployment. The updated local export has six indexable pages and is ready for an authorized deployment. A missing live test URL returned 404. Apex-domain requests failed DNS resolution in this environment; the working www domain was verified separately. This needs an owner-side DNS check, not an assumption that all users experience an outage.

Search rankings depend on relevance, useful content, competition and other signals. A technical pass cannot guarantee first-page placement or coverage of every possible phrase. Google's guidance prioritizes understandable, useful pages and notes that changes may take weeks or months to show effects. [Google SEO Starter Guide](https://developers.google.com/search/docs/fundamentals/seo-starter-guide).

## Implemented in the repository

- One owner-confirmed canonical origin in defaults, configuration examples, CI and documentation; a regression check rejects the wrong origin.
- Unique English and Arabic titles/descriptions for home, about and contact; matching canonical and Open Graph URLs; complete social-card metadata.
- Reciprocal `en`, `ar`, `en-AE`, `ar-AE` and `x-default` language alternatives, including sitemap entries. Locale signals identify equivalent pages. [Google localized versions guidance](https://developers.google.com/search/docs/crawling-indexing/localized-versions).
- Six-page sitemap excluding noindex legal drafts, 404 pages, retired routes and backups. No invented update dates or ranking-priority values.
- Optional Google/Bing verification tags, configurable before the static build. Actual property verification and submission remain external steps.
- All ten products now have visible bilingual category headings, descriptions and stable section anchors, using the same catalog as the Service/ItemList structured data. This content exists in the exported HTML before JavaScript runs.
- Donation-system language in the first hero description; descriptive headings for the four flagship sections; two additional buyer FAQs. Structured FAQ questions and answers come from exactly the same source as the rendered accordion.
- Corrected structured-data URL identifiers; consistent Organization, Website, WebPage, AboutPage and ContactPage data. No invented reviews, offers or prices added to schema.
- Crawlable homepage links to about/contact and repaired navigation to an existing homepage section. The retired `/solutions/` routes remain removed; their content-only backup remains outside public output.
- Removed 5,316 unused imported design-token declarations: `landing.css` decreased from 343,453 to 37,752 bytes before compression. English and Arabic no longer import each other's full page body. Added explicit client-logo image dimensions.
- Product-preview animation keeps text at full opacity; darker warning numerals meet contrast checks while preserving motion and layout. The site still forces light browser color-scheme, including the light 404 panel.
- Azure configuration requests immutable caching only for hashed framework assets and daily revalidation for product assets. Existing directory URL normalization and true-404 handling are preserved. Host behavior must be checked after deployment. [Azure configuration reference](https://learn.microsoft.com/en-us/azure/static-web-apps/configuration).

Google ignores the meta-keywords tag; implementation concentrates on readable content, metadata and navigation rather than adding keyword lists. [Google supported meta tags](https://developers.google.com/search/docs/crawling-indexing/special-tags). Valid FAQ markup does not make this commercial site eligible for Google's restricted government/health FAQ rich results. [Google FAQ changes](https://developers.google.com/search/blog/2023/08/howto-faq-changes).

## Verification completed

`npm run check` passed: ESLint, TypeScript, production static export and the exported-HTML SEO crawler. The crawler checks six indexable pages, unique titles/descriptions, the confirmed canonical origin, locale alternatives, social tags, H1s, links/fragments, local images, all ten products per language, FAQ/schema parity, sitemap/robots and retired-route exclusions. `git diff --check` passed.

Browser inspection covered all six indexable pages at 1440×1000, 768×1024 and 390×844, including dark-system preference with reduced motion. No horizontal overflow or broken loaded images appeared. Both homepage product sections and the 404 panel were visually inspected. Normal-motion homepage rendering was also inspected. Mobile menu opening/Escape/focus restoration, FAQ expansion, homepage-to-contact navigation and locale switching worked. Empty contact submission was rejected by browser validation with focus on the first missing field. No real email was sent.

Local HTTP checks returned 200 for `/` and `/ar/`; 404 for both solutions indexes, representative former donation-hub detail paths and a missing test path. Export checks cover the full removed directory tree. The branded 404 was inspected at desktop, tablet and mobile with light color-scheme and a visible logo.

### Lighthouse lab results

The baseline and primary comparisons use the same uncompressed Python static preview on port 3080 and default Lighthouse mobile throttling. Local browser/CPU variation affects scores. The live host separately returned `Content-Encoding: br` and HTML cache revalidation, so the uncompressed local result overstates transfer cost relative to that host.

| Run | Performance | Accessibility | SEO | LCP | CLS |
| --- | ---: | ---: | ---: | ---: | ---: |
| English mobile before | 59 | 97 | 100 | 11.1 s | 0 |
| English mobile after | 68 | 100 | 100 | 9.0 s | 0 |
| Arabic mobile after | 65 | 100 | 100 | 9.7 s | 0 |
| English desktop after | 93 | 100 | 100 | 1.7 s | 0 |
| Arabic desktop after | 93 | 100 | 100 | 1.7 s | 0.001 |

A separate gzip-enabled local preview on port 3081 scored **85 performance / 100 accessibility / 100 SEO** for English mobile (LCP 4.4 s, CLS 0) and **82 / 100 / 100** for Arabic mobile (LCP 4.7 s, CLS 0). This checks the impact of compression; it is not an Azure deployment or a before/after comparison against the uncompressed baseline. Mobile loading still has room to improve.

These are local diagnostics, not production field metrics. Mobile LCP in the uncompressed test remains slow; verify the deployed compressed build and real-user measurements. Good field thresholds are LCP ≤2.5 seconds, INP <200 ms and CLS <0.1 at the 75th percentile; Lighthouse TBT is not field INP. [Google Core Web Vitals guidance](https://developers.google.com/search/docs/appearance/core-web-vitals).

The SEO score was already 100 before this work. It confirms a limited set of technical checks, not relevance or search visibility. The gains here are broader product coverage, consistent crawlable data, fewer orphaned pages and smaller page assets.

## Work requiring the live site or owner access

No deployment, DNS change, production mutation, Search Console verification or sitemap submission was performed. Use the [launch checklist](seo-launch-checklist.md) to deploy after authorization, verify ownership, submit the new sitemap and inspect Google's selected canonical/indexing status. Search Console's URL Inspection and performance data are needed to diagnose the manager's exact query. [Google developer SEO guidance](https://developers.google.com/search/docs/fundamentals/get-started-developers).

Further growth should use evidence-backed case studies, integration details and useful product explanations, then measure non-branded impressions and qualified leads. The single-homepage structure limits how deeply each product intent can be addressed; future dedicated editorial content needs a separate routing decision and should not silently restore the removed solutions pages.
